# Дополнительные архитектурные пояснения

Этот документ фиксирует принятые решения и связанные с ними архитектурные последствия.

## C4 и границы системы

Диаграмма использует уровень C4 Container. Container в C4 — это логическая исполняемая часть системы, например приложение, сервис или база данных. Это понятие не совпадает с Docker Container.

## API Gateway

Gateway является единой точкой входа для клиентов. Его ответственность — маршрутизация запросов и общесистемные технические функции, такие как аутентификация/авторизация, rate limiting и CORS.

Gateway не владеет бизнес-данными.

## Database per Service

Каждый доменный сервис владеет своей базой. Это означает не только отдельное физическое хранилище, но и ответственность за модель данных и изменение этой модели.

Обращение к данным другого домена выполняется через публичный контракт сервиса или через доменные события. Прямой SQL-доступ к чужой БД не используется.

## Source of truth

Для каждой бизнес-сущности существует один основной владелец:

- пользователи — User DB;
- товары — Catalog DB;
- рекомендации — Feed DB;
- заказы — Order DB;
- платежи — Payment DB;
- история уведомлений — Notification DB.

Kafka может хранить события и обеспечивать их повторное чтение, но не является владельцем этих сущностей.

## Почему для разных операций разные способы связи

Синхронный HTTP используется там, где вызывающая сторона должна получить ответ сразу. Поэтому Order Service синхронно взаимодействует с Payment Service в checkout.

Асинхронные Kafka-события используются там, где дальнейшая обработка может происходить независимо. Поэтому изменения заказа/платежа могут инициировать уведомления и обновление рекомендаций без блокировки исходной операции.

## Eventual consistency

При асинхронном обмене обновление данных в разных сервисах происходит в разные моменты времени. Это означает, что кратковременное расхождение состояния допустимо, если после обработки событий сервисы приходят к требуемому состоянию.

## Идемпотентность

Асинхронная доставка может приводить к повторной обработке. Поэтому consumer должен уметь распознавать повтор и не выполнять один и тот же бизнес-эффект дважды.

Например, повторное событие `PaymentStatusChanged` не должно создать два одинаковых уведомления.

## Saga и компенсирующие действия

Если одна операция проходит через несколько сервисов, одной ACID-транзакцией между их БД её не охватить. Один из возможных production-подходов — Saga: последовательность локальных транзакций с компенсирующими действиями при сбое.

## Kafka

Kafka выбрана как event broker благодаря нескольким независимым consumers, асинхронной обработке, масштабируемости и возможности повторно читать события.

На уровне доменной модели можно использовать события:

- `CatalogChanged`;
- `OrderCreated`;
- `OrderStatusChanged`;
- `PaymentStatusChanged`;
- `UserBehaviorRecorded`.

Конкретная реализация topics, partitioning, retention, consumer groups, retry policies и DLQ относится к следующему уровню проектирования и не требуется для текущего задания.

## Персонализация

Feed Service может начинать с простого rule-based ranking. Это позволяет не создавать сложную ML-инфраструктуру до появления достаточного объёма сигналов.

Позже ranking может быть заменён или дополнен ML-моделью без изменения границ User, Catalog, Order и Payment.

## Отказоустойчивость

Асинхронное уведомление позволяет не связывать успешность заказа с доступностью Notification Service. Для production-варианта могут использоваться retry, DLQ и наблюдаемость очередей.

Если Payment Service недоступен в синхронном checkout, текущая операция не получает подтверждения платежа. Это осознанное следствие выбранной модели взаимодействия.

## Почему реализация минимальна

Практическая часть ограничена Catalog Service с endpoint `GET /health`. Это позволяет подтвердить технический запуск приложения в Docker без добавления бизнес-логики, БД, Kafka или CRUD, которые не требуются условиями задания.
